# 耗时贴着时限的用例，发现当天就处理

**规则：** 一条用例的正常耗时接近它的时限时，当天就调时限或缩短用例，并把改动提交进仓库，不靠命令行临时放宽。

Seen 1×（2026-10-13）

## 出了什么事

- `tests/browser/flood-climb.spec.mjs:349`（水淹到结束）对生产要跑 28.6–31.6 秒，默认时限是 30 秒。
- 12:44 SGT 上线后的生产检查里它超时，20 条过了 19 条，加 `--timeout=120000` 重跑 3 次才通过。13:17 的第二次上线检查直接带着 `--timeout=120000` 跑。
- 同一条用例在 GitHub runner（没有显卡）上再次超时，是 #74 第一轮 CI 的 7 条失败之一。
- 后果：同一个原因当天处理了三次。

## 修复的提交

`85719cc`（#74）：`playwright.config.mjs` 在 `CI` 下把时限改成 90 秒。本机和对生产跑仍是 30 秒，所以对生产检查还得手动加 `--timeout`。**只修了 CI 这一半。**

## Done right

- 两次上线评论都写了放宽时限这件事和原因，没有只报「43 / 43」。
- #74 把 CI 上的帧率下限和时限分开处理，并写了 runner 上的实测帧率。
