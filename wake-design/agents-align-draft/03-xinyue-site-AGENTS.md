# 心月网站：产品与交互要求

以下要求来自用户对下一版管理后台和后续开发方式的明确要求。它们是设计、开发与验收约束，不表示对应功能已经实现或上线。当前实现和验证范围以源码、README.md、DEPLOYMENT.md 为准。

完整需求设计见 [手机后台设计](docs/plans/2026-09-28-1710-feat-xinyue-mobile-studio-plan.md)。

## 主要使用者与自主操作

- 主要操作者是小学四年级的馨玥。她需要自己登录后台、管理游戏与创作口令，并负责网站的后续修改和上线。
- 日常创作、管理、开发、发布和恢复旧版不设置家长审批步骤，也不把问题转交给家长代操作。
- 她应能用自然语言描述想法完成操作，不需要写代码、操作终端、管理代码仓库或执行部署命令。按钮和明确选项可作为辅助。
- 修改想法不等于上线授权。由她本人决定何时把预览中的改动公开，不额外要求家长批准。

## 登录与找回：已选择，待实现

- 馨玥使用自己的登录密码进入后台，并用自己保存的私密找回卡恢复访问；不依赖邮箱、手机号或家长账号。
- 她的登录凭据与分给朋友的创作口令分开。朋友不能凭创作口令取得后台管理权限。
- 账号需要持久保存作品归属，不能把浏览器 Cookie 当作唯一身份记录。
- 密码和找回卡都丢失时，不能保证自动找回；不要承诺无法验证身份的恢复能力。

## 四年级能理解的交流

- 对她的界面文案、问题、进度、错误和操作结果，都用四年级学生能理解的具体说法。
- 一次只问一个需要她决定的问题；提供少量清楚的选择，允许她用自己的话回答。
- 让她决定想做什么、喜欢什么、是否公开，不让她选择技术实现细节。
- 不要求她理解 Git、CI、API、数据库迁移、构建或部署等术语；例如使用“看看效果”“让大家看到新版”“恢复到这个版本”。
- 不用装幼稚的口吻，不责备她的表达。说明实际完成了什么、还没完成什么，以及下一步能做什么。
- 后台必须支持中文和英文，覆盖页面、按钮、对话提问、选项、进度、错误与结果提示。两种语言都要让四年级学生容易理解。
- 沿用现有网站的中英切换原则：不重载页面、不清空输入、不丢失任务或试玩状态，不擅自翻译作者内容；正在进行的生成任务不因界面切换而改变其提交时的语言。

## 与现有网站保持同一视觉风格

- 后台、公开页面及中英文界面遵循同一套视觉规范，不另做一套成人管理系统样式。
- 以现有 `public/styles.css` 为基准：米白背景、浅紫主色、薄荷绿和桃色辅助色、圆角卡片、胶囊按钮及现有字体风格。
- 新增页面和状态保持颜色、间距、按钮层级和反馈方式一致。为手机触屏和儿童阅读调整字号、按钮大小与布局，不等于更换视觉风格。
- 黑白手机草图仅用于确认交互顺序，不是最终配色，也不是已经实现的后台。

## 已确认的后台操作方向

- 首页以聊天式的“说想法”为主入口，底部保留“说想法、游戏、口令、记录”四个入口。
- 游戏、创作口令和版本记录提供简单的按钮操作；也能通过自然语言提出相同的管理要求。
- 操作顺序先说清想法，再看效果与试玩，由馨玥决定是否让大家看到新版。代码与部署细节不作为她必须完成的步骤。
- 用户已确认这一交互方向，不表示草图中的账号、检查、恢复、配额数值或权限机制已经实现或完成选型。

## 后台手机优先

- 手机适配是后台的核心验收条件，不只适用于公开首页。
- 登录、描述修改、回答问题、查看预览、试玩、管理游戏、管理创作口令、确认上线、查看修改记录和恢复旧版，都必须能在手机上完成，不能依赖电脑。
- 不使用只能靠鼠标悬停、右键、拖拽或键盘快捷键完成的操作；必要操作应有触屏替代方式。
- 小屏幕和软键盘打开时，输入、主要按钮和反馈仍应可用；不以缩小桌面页面代替手机布局。
- 手机验证覆盖完整操作流程和失败状态，不仅检查首页截图。模拟尺寸与真实设备验证须分别报告，不能混称。

## 权限与执行边界

- 不需要家长日常审批，不等于让孩子或生成代码的模型接触云账号密钥、付款凭据，或取得无限支出权限。
- 代码、检查、发布和恢复过程须封装在后台；不能只隐藏按钮，却让模型绕过权限检查。
- 本文件不单独授权新增付费资源、扩大云账号权限、操作其他网站或发布尚未获准的改动。设计、实现、验证和已上线状态必须区分。

## Orca 与提交

- 任务由开发 bot 派给 Orca 里的 coding agent。一个 Linear issue 一个工作区一个 PR；不在别的任务的工作区里改东西。不指定用哪种 coding agent。
- 动手前读本工作区 `AGENTS.md`、`docs/solutions/LESSONS.md` 和 `docs/decisions.md`。工作区的 AGENTS.md 比主分支旧（没有本段或没有测试规矩）时，先 rebase 到最新 base，或按派活里附的测试规矩执行。
- 派活写明可以 push / 开 PR / 合并 / 部署的就照做；没写就不做，停在本地提交并在报告里写明。（Zack approved 2026-10-16）
- 超过 15 分钟的命令用 notify-run 包：`notify-run --bot xinyue --task "<编号> <简述>" -- <command>`。做完或卡住不要静默停在输入框：最后一条消息写「结论 + 报告路径」。
- 不用 `git add .` / `git add -A`。每个 PR ≤2000 行，超了拆叠加 PR。

## 部署与 CI

- 部署和写 secret 用 Cloudflare CLI（`npx cf` / `cf`），不用 `wrangler deploy`、`wrangler secret`。（`wrangler dev`、`wrangler d1 migrations apply --local` 这类本地命令可以继续用。）
- 部署走 Cloudflare Workers Builds：`staging` → testing（`*-test` 资源），`main` → production。（应用时核实：心月实际分支名、是否已接 Workers Builds；未接则改成实际现状或「迁移中」。）
- GitHub Actions 只跑测试，不部署。GitHub 里不放 Cloudflare token。
- 部署到 testing 或生产前，该 commit 的 CI 必须跑完且全绿；被取消的不算。合并锁定审过的 sha：`gh pr merge --match-head-commit <sha>`。
- 生产部署和远程 D1 迁移只在派活明确授权时做，并记进 `docs/operations/` 对应文件（版本号、回滚目标）。

## 测试规矩（Zack）

以下原文照录，适用于本仓库所有改动的测试与验证：

- NEVER write unit tests after you write code.
- Highly prefer E2E tests as the sole testing mechanism, produce a verifiable and repeatable artifact at the end.
- If you must test in isolation, FIRST write all the ways it could fail, THEN write the code.

写完代码不补单元测试。已有的 `npm test` 单测和 CI 不删、不削弱，但不算验收。

E2E 要诚实：

- 测真实部署和真实用户流程。不 mock、不 stub、不伪造接口返回，不跳过步骤。用了测试替身的 Playwright 跑法只能写成「本地替身检查」，不能写成 E2E。
- 不放宽断言，不挑着重跑。失败就照实报告；如果是测试本身写错了，写明原因和改了什么，并保留失败那次的结果，再把整套重跑一遍。
- 结束时留下别人能复现的产物：命令、URL、commit、构建 id、版本号，以及截图或日志。
- 模拟手机尺寸和真机要分开报告。没跑的、跳过的项目要写明。

每个 PR 的 E2E：

- 每个 PR 都要在**该 PR 当前 head commit** 上跑真实 E2E（testing 环境）。单测过、CI 绿都不能替代。head 变了就重跑，旧 commit 上的结果不算。
- 没有 E2E 结果的 PR 不转 ready、不请人 review。
- 会调用真实模型、产生费用的验收，先报次数和预算等批准。

PR 描述 / PR 评论里的 E2E 报告，全部写全：

```
E2E（PR head）
- 命令：<完整命令，不含密钥>
- 环境/硬件：<testing URL；跑在哪台机器；模拟尺寸（如 390×844）还是真机（型号/系统）>
- commit：<PR head 的完整 sha>
- 结果：<通过 N / 失败 M / 跳过 K；失败用例名>
- 产物：<截图/日志/录屏路径；Worker 部署版本号>
回退测试：<把旧代码放回去，这条 E2E 确实会挂：是/否/没跑>
回滚：<回滚到哪个 Worker 版本，怎么回滚>
没跑的：<逐项写「没跑」和原因>
单元测试：CI covers unit tests
```

把失败说成「与本次改动无关」时（夜审 2026-10-15 升级，第 3 个不同日子，见 `docs/solutions/lessons/name-and-rerun-failures-called-unrelated.md`）：

- PR 评论写清用例名（文件:行）、报错原文，以及同一用例在 base 上的结果（CI 链接或重跑记录）；拿不出就写「没对照 base」。
- 重跑了要写：整轮还是只重跑失败 job、谁定的、重跑结果。`status.md` 和汇报也不能只写「无关」「偶发」「重跑全绿」。
- 同一用例或同一批失败第二次出现：先搜 Linear，有单就补评论记次数，没单就开单查；不许再照抄「无关，重跑」。
