## 怎么重跑

在 iMac 的仓库根目录：

```bash
wake/tests/heartbeat-watch-ssh.sh
```

要求本机 Orca 有 environment `mba`、`grok-bot`，能 `ssh mba`，MBA 能 `ssh imac`。整个目录会被重写（有 `.hb-drill` 标记才清空）。回放数据要重录时先跑 `wake/tests/heartbeat-watch-ssh.sh --record`。

heartbeat-watch 都用临时 `HB_STATE_DIR`；除 S12、S13 外都带 `--dry-run`、用假 webhook 目录（`127.0.0.1:9` 的假地址），不发叫醒、不读真凭据。S12、S13 不带 `--dry-run`（要看写下的 state.json 和 `@@HB`）：webhook 目录是空的，PATH 里放了只记录调用的假 curl。S12 第一次查不到时 heartbeat-watch 走 `continue`，到不了发告警那步；S13 读的是真的 ops · 01，正常时不发告警，万一判中断，没有 webhook 配置、curl 也是假的，发不出去。lockf 的锁文件、lock-held-alert 的状态文件都放在临时目录里，没碰 `~/.orca-state/heartbeat-watch/` 下的真文件（S10 核对）；precheck 里的 `~/.orca-state/bin/lock-held-alert` 换成了仓库里 `scripts/lock-held-alert` 的临时副本。lock-held-alert 不看 `--dry-run`：S15 里它真发告警，发给假 webhook 配置（`STUCK_FORCE_BOT=ops-system`，`127.0.0.1:9` 的假地址），PATH 里的假 curl 记下请求体、回 200，不连网络；别的场景到不了它发告警的那一步（没到 45 分钟）。S12.old、S14 的 timeout 第一轮到超时时，演练脚本照 Orca 的做法给它自己起的预检进程组发 SIGTERM、2 秒后 SIGKILL；S14 的 kill、term、crash 核对 pid、ppid（演练的 shell）、命令名（lockf）以后，只给演练自己起的 lockf 发 SIGKILL、SIGTERM、SIGSEGV，它起的 sleep 不发信号、等它自己结束。没有给演练以外的进程发过信号。crash 让 macOS 给 lockf 写一份崩溃报告 `lockf-<日期>-<时间>.ips`，每台每跑一次多一份：iMac 上在 `~/Library/Logs/DiagnosticReports/`，MBA 上在 `/Library/Logs/DiagnosticReports/`；两台「共享 Mac 分析」都关着，报告只留在本机；演练不删它（FAILURE-MODES F36、F37）。orca 只用 `automations list / show / runs`；不往 `~/.orca-state/bin/` 装文件；MBA 上只用 `mktemp -d` 的临时目录，跑完删掉。

- MBA 那条的少见情况：还没见过心跳、心跳又过期，而且 runs 前两次各卡满 70 秒，再加一次 list，最坏 296 秒，加起动约 4 秒，在 330 秒的超时以内。没演练。
- lock-held-alert 真等 45 分钟：没跑。S15 主线把阈值改成 0.25 分钟；默认的 45 分钟由 S15 的 .45 看，状态文件是演练写的（FAILURE-MODES C17）。
- lock-held-alert 的告警发不出去（没有 webhook 配置、POST 失败）、「已恢复」发不出去：没演练，S15 只走了发成功的路（假 curl 回 200，A51）。
- 两个 lock-held-alert 同时写状态文件：没演练（A50）。
- 收件方（Coding助手）怎么处理 `source` 是 `lock-held-alert` 的 `heartbeat_stale`、`heartbeat_recovered`：没验证，告警只发给了假 curl（C18）。
- lockf 自己真的段错误：没有。S14 的 crash 是从外面给 lockf 发 SIGSEGV 模拟的（C20）。
